# The xCloud protocol, as this client implements it

A complete map of what goes over the wire, written 2026-09-06 from the code
plus traffic captured from live sessions the same night. Where something is
observed it says so; where it comes from a reference client and has never been
seen here, it says that too. The original working notes are the
route notes; this is what was actually built.

Three layers, in order of use:

1. **GSSV REST** over HTTPS — authentication, catalogue, session lifecycle,
   SDP and ICE exchange. Everything up to the point where media flows.
2. **WebRTC** — DTLS/SRTP transport carrying H.264 and Opus, plus SCTP data
   channels.
3. **The application protocol** on those data channels — JSON control
   messages and binary input reports.

---

## 1. GSSV REST

### Authentication chain

Five hops, all in [auth.cpp](../src/gnx/auth.cpp):

| Step | Endpoint | Gives |
|---|---|---|
| Device code | `login.microsoftonline.com/consumers/oauth2/v2.0/devicecode` | user code + verification URL |
| Poll / refresh | `.../oauth2/v2.0/token` | MSA access + refresh token |
| Xbox user token | `user.auth.xboxlive.com/user/authenticate` | user token |
| XSTS authorize | `xsts.auth.xboxlive.com/xsts/authorize`, relying party `http://gssv.xboxlive.com/` | gssv token + uhs |
| Streaming login | `https://{offering}.gssv-play-prod.xboxlive.com/v2/login/user` | `gsToken`, region list |

Scope `xboxlive.signin openid profile offline_access`. The streaming login
carries `x-gssv-client: XboxComBrowser` and takes `{"token", "offeringId"}`.
Its response holds `offeringSettings.regions[]`; **the region with
`isDefault == true` supplies the `baseUri` used for every later call**, with
`Authorization: Bearer <gsToken>`.

Three offerings, all fetched at sign-in:

- `xgpuweb` — Game Pass cloud. The normal path.
- `xgpuwebf2p` — ad-supported free-to-play; needed for titles the account has
  no other route to.
- `xhome` — your own console (remote play). Returns a **different host shape**,
  observed: `https://uks.core.gssv-play-prodxhome.xboxlive.com`. Failure here
  is normal (no console on the account) and is kept in `home_error` rather
  than thrown.

A separate XSTS authorize against relying party `http://xboxlive.com` gets the
token for `profile.xboxlive.com` (gamertag, gamerscore, avatar).

### Session lifecycle

All against the region `baseUri`, with an `X-MS-Device-Info` header describing
the client (see [RESOLUTION.md](RESOLUTION.md) — its `os.name` and
`displayInfo` matter far less than they appear to).

```
POST /v5/sessions/cloud/play   {titleId, settings, ...}   -> {sessionPath}
POST /v5/sessions/home/play    {serverId, settings, ...}  -> {sessionPath}
GET  {sessionPath}/state       poll ~700 ms
POST {sessionPath}/connect     {"userToken": <Passport LPT>}   at ReadyToConnect
POST {sessionPath}/sdp         our offer                        at Provisioned
GET  {sessionPath}/sdp         until != 204                     -> answer
POST {sessionPath}/ice         our candidates
GET  {sessionPath}/ice         until != 204                     -> theirs
POST {sessionPath}/keepalive   empty body, on its own thread
DELETE {sessionPath}           stop
```

States: `New`, `WaitingForResources`, `Provisioning`, `ReadyToConnect`,
`Provisioned`, `Failed`. `sessionPath` comes back **without** a leading slash.

Traps that cost real time, all now handled:

- **HTTP 204 on the SDP and ICE GETs means "not yet", not an error.**
- **Home sessions attach an `errorDetails` object with every field null to
  perfectly good responses.** Only a non-null field inside it is a real
  failure ([session.cpp](../src/gnx/session.cpp), `is_real_exchange_error`).
- The Passport token for `/connect` is short-lived: mint it at
  `ReadyToConnect`, not at sign-in.
- Only one session per account. `cleanup_stale_sessions()` runs first,
  parameterised by platform (`cloud` / `home`).

Other endpoints: `GET /v6/servers/home` (consoles), `GET /v2/titles` (~2600
entries with entitlement flags), `GET /v2/titles/mru?mr=25`,
`GET /v1/waittime/{titleId}` (queue depth — **response shape unverified**, see
the M7 notes (project notes)). Names and box art come from the unauthenticated
`displaycatalog.mp.microsoft.com/v7.0/products?bigIds=`.

## 2. WebRTC

The offer is generated by libpeer and then munged as a string. **Only the
offer is ours to shape; the answer is passed to libpeer byte for byte** —
reserialising it once corrupted the CRLFs, which made libpeer read the ICE
ufrag with a stray CR and send STUN checks with the wrong integrity key, so
the connection simply never completed.

The video m-line matters more than it looks. xCloud pattern-matches it against
per-device codec templates: a half-match gets the video track rejected
outright (`m=video 0`), and a template miss without `packetization-mode` lands
in a minimal-capability fallback pinned to single-NALU packets at about
150 kbps. What works, from [sdp.c](../third_party/libpeer/src/sdp.c):

```
m=video 9 UDP/TLS/RTP/SAVPF 102
a=rtpmap:102 H264/90000
a=fmtp:102 level-asymmetry-allowed=0;packetization-mode=1;
           profile-level-id=42e01f;max-fs=3600;max-mbps=108000
a=rtcp-fb:102 goog-remb / ccm fir / nack / nack pli
a=recvonly
```

Munges applied on top ([session.cpp](../src/gnx/session.cpp)):

- `sdp_force_stereo` — `useinbandfec=1` gains `;stereo=1`.
- `sdp_scale_video_caps_1080` — for the 1080 tiers only.
- `sdp_set_h264_level_32` — **xHome only**: the console's agent wants level
  3.2 (`42e020`) where the cloud accepts 3.1.
- `sdp_set_video_caps` — research only.

**The declared decode limits are decorative.** Measured: offering level 2.1
with `max-fs=792` got the level echoed back in the server's answer and 1280x720
(3600 macroblocks) sent anyway. The encoder is configured server-side and does
not consult the receiver's stated capability. Do not expect anything here to
constrain the stream.

ICE candidates are posted explicitly to `/ice` as well as being embedded in
the offer, because the official client does that and getting the shape wrong
makes xCloud withhold its own candidate.

## 3. The data-channel protocol

Four channels, created by the client, all reliable and ordered
([xcloud_protocol.hpp](../src/gnx/xcloud_protocol.hpp)):

| Label | Protocol | SID | Carries |
|---|---|---|---|
| `control` | `controlV1` | 0 | authorization, gamepad presence, keyframe and resolution requests |
| `input` | `1.0` | 2 | binary pad reports out; rumble in |
| `message` | `messageV1` | 4 | the handshake and all JSON properties |
| `chat` | `chatV1` | 6 | opened, never used here |

`input` must be reliable and ordered: a v1 report is absolute pad state
numbered by a running sequence, and the server stops applying input the moment
it sees a gap. Loss tolerance is a protocol feature of the newer "2.0" model
(`unreliableinput` + `reliableinput`, frame deltas with acks), not something
to fake by loosening the channel.

### Bring-up order

1. Client sends `{"type":"Handshake","version":"messageV1","id":...}` on
   `message`.
2. Server replies `HandshakeAck` (observed).
3. Client then sends, in order:
   - `authorizationRequest` with the fixed access key, on `control`
   - `gamepadChanged {index, wasAdded}`, on `control`
   - `userRequestedResolutionUpdate {resolutionAlias}`, on `control` — **this
     is the real resolution lever**, enum `Auto / 720 / 720HQ / 1080 /
     1080HQ / 1440`
   - six `message`-channel properties: `systemUi/configuration`,
     `properties/clientappinstallidchanged`,
     `characteristics/orientationchanged`,
     `characteristics/touchinputenabledchanged`,
     `characteristics/clientdevicecapabilities`,
     `characteristics/dimensionschanged`
   - `client_metadata` binary report on `input`

`clientdevicecapabilities` and `dimensionschanged` carry `maxWidth`,
`maxHeight`, `maxPixels`, `preferredWidth`/`preferredHeight` and
`maxBitrateKbps`. These are the fields the GDK's
`XGameStreamingGetDisplayDetails` hands to the **title**, which is why they do
nothing unless the game has adopted `XGameStreamingSetResolution` — Fortnite
has, most have not.

Every `message`-channel payload is double-encoded: a `{"type":"Message",
"target":..., "content":...}` envelope whose `content` is itself a JSON
*string*.

### What the server sends back

Observed live, 2026-09-06. This is the complete set seen in ~20 sessions:

| Target / type | Content | We do |
|---|---|---|
| `HandshakeAck` | — | trigger the bring-up above |
| `/streaming/properties/titleinfo` | `{focused, state, titleaumid, titleid}` | log only |
| `/streaming/touchcontrols/showtitledefault` | empty | log only |
| `/streaming/sessionLifetimeManagement/serverInitiatedDisconnect` | `{reason}` e.g. `KickForStopCommand` | end the session |

Nothing has ever been observed arriving on `control` or `chat`. The `input`
channel receives vibration reports (type 128 in green-nx); this handheld has
no motors, so they are counted as an input-liveness signal and discarded.

**`titleinfo` is unused and probably should not be.** It carries the real
title id and focus state, which would let the client show what is actually
running and notice a title change — worth considering for the library screen.

### Input reports

Little-endian binary on `input`. Report type 2 is a gamepad frame: a
`uint16` type, `uint32` running sequence, `double` elapsed ms, a count, the
pad index, a `uint16` button mask, four `int16` axes, two `uint16` triggers, a
`uint32` unit id and four trailing constant bytes. Type 8 is the client
metadata sent once at start.

The Y axes are negated on the way out; the sequence must be contiguous, so a
packet that is built but never handed to SCTP gives its number back
(`rollback_sequence`).

## 4. Media and feedback

Video is H.264 in RTP, reassembled by [video_jitter.cpp](../src/media/video_jitter.cpp)
into Annex-B access units; audio is Opus. Three feedback mechanisms run back
up the RTCP path:

- **NACK** on a sequence gap, plus a second ask at 70 ms — one retransmit
  round trip is 25-40 ms, and on the handheld's Wi-Fi 25 of 64 NACKed frames
  were still lost after the first.
- **PLI** when a frame is given up on. Exponentially backed off (300 ms
  doubling to 2 s) while still waiting, because a fixed short interval makes
  the client ask for an IDR per non-IDR frame and libwebrtc answers every one
  — an IDR storm precisely while the link is losing packets. **Measured
  round trip: 94 ms at 720p, 69 ms at 360p**
  ([PERFORMANCE.md](PERFORMANCE.md)).
- **REMB**, the receive-bandwidth estimate we advertise, backed off on loss
  and ramped when clean.

The bitrate cap is declared through `clientdevicecapabilities.maxBitrateKbps`,
**not** through `b=AS`/`b=TIAS` lines — working clients send none.

## 5. Not implemented

Deliberate, with reasons:

- **Input protocol "2.0"** (`unreliableinput`/`reliableinput`, deltas + acks).
  v1 works and is simpler; 2.0 matters on a lossy link, which is this
  device's situation, so it is the most defensible thing on this list to
  revisit.
- **Rumble.** No motors.
- **Touch controls.** The server offers them (`showtitledefault` observed);
  there is no touchscreen.
- **`chat`.** Channel opened for protocol fidelity, never used.
- **HEVC / HDR.** Declared false; the decoder is software H.264.
- **`titleinfo` handling.** See above — the one gap that looks like an
  oversight rather than a choice.
